### ユーザーストーリー1 - 商品選択・決済フロー (優先度: P1)

ユーザーがログイン後、商品一覧から商品を選択して擬似決済を完了し、決済完了結果を確認できることを保証します。このストーリーは5つの連続した画面フロー（商品選択 → 決済 → 支払い確認 → 決済処理 → 完了）から構成され、決済デモの主要ユースケースを実装します。

**この優先度の理由**: ユーザーが実際に商品を購入してデモシステムが動作することを検証するための主要フロー。すべてのトランザクション記録とDiscord連携の対象となり、ビジネス発注の中核価値を提供します。

**独立テスト方法**: ユーザー (user ロール) でログインして、商品選択から決済完了まで全フロー実行し、Supabase の payments テーブルにレコード (status=succeeded) が作成され、取引IDが取得できることを検証します。

**受け入れシナリオ**:

1. **前提条件**: ユーザーがログイン済み、複数の商品がシステムに登録済み
   **実行**: ユーザーが商品一覧を表示 → 商品1つを選択 → 決済金額を確認 → 「支払い完了」ボタンをクリック
   **期待結果**: 完了画面が表示され、取引ID と ステータス (成功) が表示される。Supabase payments テーブルに新規レコード (user_id, product_name, amount_jpy, status=succeeded, created_at) が記録される

2. **前提条件**: 決済完了後画面を表示中
   **実行**: ページをリロードまたは別タブで same transaction_id を参照
   **期待結果**: 同じ取引IDで同じ取引情報が表示される（トランザクション参照の一貫性）

3. **前提条件**: ユーザーが支払い確認画面にいる
   **実行**: 1分以上待機（この間 Discord リトライが実行される可能性）
   **期待結果**: 完了画面で Discord 通知ステータス (成功 / 失敗 / 再試行中) が表示される

---

### ユーザーストーリー2 - 商品選択画面表示 (優先度: P2)

商品選択画面で複数の商品が正確に表示され、ユーザーが選択できることを保証します。このストーリー単独で、UI/UX と商品データ取得レイヤーの品質を検証できます。

**この優先度の理由**: データベースと UI の連携を単独で検証でき、故障時の隔離テストが可能。Story 1 の下位構成コンポーネントですが、独立テストの価値があります。

**独立テスト方法**: ログイン後、商品選択画面を表示し、登録されたすべての商品が表示され、各商品の商品名 / 金額が正確に表示されることを検証します。

**受け入れシナリオ**:

1. **前提条件**: ユーザーがログイン済み、3つ以上の商品が商品マスタに登録済み
   **実行**: 商品選択画面へ遷移
   **期待結果**: すべての商品が一覧で表示され、商品名と金額（JPY）が正確に表示される

2. **前提条件**: 商品選択画面を表示中
   **実行**: 商品を1つ選択 → 「決済へ」ボタンをクリック
   **期待結果**: 選択した商品が決済画面に渡され、決済画面で同じ商品情報が表示される

---

### ユーザーストーリー3 - 支払い確認画面表示と完了 (優先度: P2)

ユーザーが支払い確認画面で取引情報（商品名、金額、ユーザー名）を確認し、「支払い完了」ボタンをクリックしてサーバーサイド処理をトリガーできることを保証します。

**この優先度の理由**: サーバーサイド処理の起動と Supabase トランザクション作成を単独検証できます。Story 1 の分離可能なコンポーネント。

**独立テスト方法**: 支払い確認画面を表示し、正確な取引情報が表示され、「支払い完了」クリック後にサーバーが payments レコードを作成し、取引ID が生成・レスポンスされることを検証します。

**受け入れシナリオ**:

1. **前提条件**: ユーザーが支払い確認画面まで到達済み
   **実行**: 画面に表示された商品名・金額・ユーザー名が正確であることを確認 → 「支払い完了」をクリック
   **期待結果**: サーバーが payments テーブルにレコード作成（UUID id、ユニーク transaction_id、status=succeeded）し、完了画面に遷移。取引IDが表示される

---

### エッジケース

- 商品未選択で「決済へ」クリック → UI で選択必須にして防止
- ネットワーク遅延により支払い完了処理中にページが閉じられた場合 → サーバーはトランザクション作成済み、ユーザーは transaction_id が返却されないが管理画面で確認可能
- 同一ユーザーが短時間に複数の決済トリガー → 各決済は独立した UUID と transaction_id を持つため並行処理対応
- 削除済み商品への古い参照 → payment の product_name は非正規化されているため表示可能。ただし再決済時に商品がない場合はエラー画面
- **Payment作成時サーバーエラー** → エラー画面表示し「トランザクション作成失敗。管理者に連絡」と案内

## 要件 *(必須)*

### 機能要件

- **FR-001**: システムは認証無しで商品選択ページにアクセスできません。ユーザーが Supabase Auth にてログイン済みの場合のみアクセス可能
- **FR-002**: ユーザーは「商品選択 → 決済 → 支払い確認 → 支払い完了」の4ステップフローを完了できる
- **FR-003**: 商品選択画面は Supabase products テーブルから登録済みすべての商品を取得して表示（商品名、金額JPY、応答時間目標 1000ms p95）
- **FR-004**: 決済画面は選択した商品の詳細情報を表示
- **FR-005**: 支払い確認画面は商品名、金額、ユーザー名を表示
- **FR-006**: ユーザーが「支払い完了」をクリック後、システムは payments テーブルに新規トランザクション (status=succeeded) を作成し、ユーザーに transaction_id を返す（応答時間目標 1000ms p95）
- **FR-007**: 完了画面はトランザクションID と支払いステータス (成功 / 失敗) を表示
- **FR-008**: 完了画面は Discord 通知ステータス (成功/失敗/再試行中) をリアルタイムポーリング（1秒間隔）で更新表示。初期表示は「送信中...」のプレースホルダー、その後サーバーの discord_notifications テーブルを定期クエリして反映

### 主要エンティティ

- **Product（商品）**: Supabase products テーブルに登録される販売商品。属性: id（UUID）、product_name（商品名、テキスト）、amount_jpy（金額、整数）、created_at（タイムスタンプ）。RLS有効化により全ユーザーが読み取り可能
- **Payment（取引）**: ユーザーによって作成される1件の購入取引。属性: id（UUID、主キー）、transaction_id（表示用、ユニーク）、user_id（auth.uid参照）、user_name（ユーザー表示名、Supabase Auth user_metadata.display_name から取得して決済作成時に非正規化保存）、product_name、amount_jpy、status（pending/succeeded/failed）、created_at（タイムスタンプ）。RLS有効化により、ユーザーは自分の取引のみ表示可能
- **User（ユーザー）**: Supabase Auth により管理される認証ユーザー。属性: uid（UUID）、email、user_metadata（display_name ユーザー表示名含むロール情報）

### 非機能要件

- **NFR-001**: API 応答時間は 1000ms (p95) 以下。対象: 商品一覧クエリ、payment 作成、通知ステータスクエリ
- **NFR-002**: 完了画面の Discord 通知ステータスポーリングは 1秒間隔で実行、最大60秒間（キャンセル可能）
- **NFR-003**: RLS は payments テーブルおよび discord_notifications テーブルで有効化。ユーザーは自分の取引・通知のみ表示可能

## 成功基準 *(必須)*

### 測定可能な成果

- **SC-001**: ユーザーは商品選択から支払い完了までの全フロー (5画面) を3分以内に完了できる
- **SC-002**: 完了画面でトランザクションID が即座（1秒以内）に表示される
- **SC-003**: 取引レコードが Supabase payments テーブルに確実に（100%）記録される
- **SC-004**: ユーザーは複数の異なる商品で連続決済でき、各決済が独立したトランザクション ID を取得する
- **SC-005**: Discord 通知ステータスが完了画面に正確に反映される（通知成功時は「成功」、最大5回リトライ後失敗時は「失敗」と表示）
- **SC-006**: 取引記録の user_name、product_name、amount_jpy がユーザー入力・選択内容と100%一致する
